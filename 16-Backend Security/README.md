#  Backend Security Notes (ব্যাকএন্ড সিকিউরিটি গাইড)

**Sriniously** চ্যানেলের **"20. Backend Security: Everything You Need to Know"** ভিডিওর ওপর ভিত্তি করে তৈরি পূর্ণাঙ্গ নোট।

##  ১. মূল বিষয়  (The Golden Rule)

> **"ব্যবহারকারীর ইনপুটকে কখনো বিশ্বাস করব না এবং ডেভেলপারের ধারণা বা অ্যাসাম্পশন নিয়ে প্রশ্ন তুলুব।"**

আক্রমণকারীরা (Attackers) এটি দেখেন না যে আমি আপনি কোন প্রোগ্রামিং ল্যাঙ্গুয়েজ বা ফ্রেমওয়ার্ক ব্যবহার করছি। তারা কেবল খোঁজে **ডেভেলপার কোথায় ভুল ধারণা বা অ্যাসাম্পশন (Assumption) করেছে:**
* ডেভেলপার ধরে নিয়েছে ক্লায়েন্ট বা ফ্রন্টএন্ড থেকে আসা ডাটা সবসময় নিরাপদ ও ক্লিন ।
* ধরে নিয়েছেন সব রিকোয়েস্ট কেবল তাদের অফিশিয়াল অ্যাপ/ওয়েবসাইট থেকেই আসছে ।
* ধরে নিয়েছেন সাধারণ ব্যবহারকারী ব্রাউজারের Network Tab খুলে API বা রিকোয়েস্ট পরীক্ষা করবেন না ।

##  ২. সাধারণ সিকিউরিটি হুমকি ও প্রতিরোধের উপায়

### ১. SQL Injection (SQLi)
* **কী এবং কেন হয়?** ব্যবহারকারীর ইনপুটের সাথে অনাকাঙ্ক্ষিত SQL কমান্ড মিলিয়ে ডাটাবেজে পাঠিয়ে দিলে এ ধরনের আক্রমণ ঘটে ।
* **ক্ষতি:** গোপন ডাটা চুরি, অথেনটিকেশন বাইপাস করা বা ডাটা মুছে ফেলা ।
* **প্রতিরোধ:**
  * **Parameterized Queries / Prepared Statements** ব্যবহার করা।
  * সঠিক উপায়ে ORM (যেমন: Prisma, TypeORM, Drizzle) ব্যবহার করা।
  * স্ট্রিং কনক্যাটেনেশন (String Concatenation) করে সরাসরি SQL কুয়েরি তৈরি না করা ।

  #  SQL Injection (SQLi) Example & Prevention

SQL Injection হলো একটি সিকিউরিটি Vulnerability, যেখানে আক্রমণকারী কোনো ইনপুট ফিল্ডের মাধ্যমে ক্ষতিকারক SQL কোড ব্যাকএন্ডে পাঠিয়ে ডাটাবেজের ওপর অনাকাঙ্ক্ষিত কুয়েরি চালায়।

---

##  ১. ঝুঁকিপূর্ণ কোড (Vulnerable Code Example)

মনে করি, ব্যবহারকারীর লগইনের জন্য ব্যাকএন্ডে নিচের মতো স্ট্রিং কনক্যাটেনেশন (String Concatenation) করে SQL কুয়েরি লেখা হয়েছে:

```sql
-- ব্যাকএন্ডে তৈরি হওয়া কুয়েরি
SELECT * FROM users WHERE username = 'USER_INPUT' AND password = 'USER_INPUT';

SELECT * FROM users WHERE username = 'admin' --' AND password = '...';

SELECT * FROM users WHERE username = '' OR '1'='1' AND password = '...';

// বিপজ্জনক! স্ট্রিং টেমপ্লেট দিয়ে ইনপুট বসানো হয়েছে
const query = `SELECT * FROM users WHERE username = '${req.body.username}' AND password = '${req.body.password}'`;
db.query(query); 

// নিরাপদ! ডাটাবেজ ইনপুটকে কেবল "ডাটা" হিসেবে দেখবে, কোড হিসেবে নয়
const query = 'SELECT * FROM users WHERE username = $1 AND password = $2';
db.query(query, [req.body.username, req.body.password]);

---

### ২. Cross-Site Scripting (XSS)
* **কী এবং কেন হয়?** ওয়েবসাইটে ক্ষতিকারক ক্লায়েন্ট-সাইড স্ক্রিপ্ট (JavaScript) ইনজেক্ট করে দেওয়া ।
* **ক্ষতি:** কুকি বা সেশন চুরি করা, ইউজার সেশন হাইজ্যাক করা।
* **প্রতিরোধ:**
  * ফ্রন্টএন্ড ও ব্যাকএন্ড উভয় স্থানে ডাটা সেনিটাইজ ও এস্কেপ (Sanitize & Escape) করা।
  * কুকিতে **`HttpOnly`** এবং **`SameSite`** ফ্ল্যাগ ব্যবহার করা যাতে জাভাস্ক্রিপ্ট থেকে কুকি রিড করা না যায়।
  * কড়া **Content Security Policy (CSP)** হেডার সেট করা।

---

### ৩. Cross-Site Request Forgery (CSRF)
* **কী এবং কেন হয়?** একজন লগইন করা ব্যবহারকারীকে ট্রিক করে তার অজান্তেই সার্ভারে কোনো অনাকাঙ্ক্ষিত রিকোয়েস্ট পাঠানো ।
* **ক্ষতি:** ব্যবহারকারীর অজান্তে পাসওয়ার্ড পরিবর্তন বা টাকা ট্রান্সফার হয়ে যাওয়া।
* **প্রতিরোধ:**
  * স্টেট পরিবর্তনকারী রিকোয়েস্টে (POST, PUT, DELETE) **CSRF Token** ব্যবহার করা।
  * কুকিতে `SameSite=Lax` অথবা `SameSite=Strict` সেট করা।

---

### ৪. Server-Side Request Forgery (SSRF)
* **কী এবং কেন হয়?** ব্যাকএন্ড সার্ভারকে বাধ্য করা কোনো অভ্যন্তরীণ (Internal) নেটওয়ার্ক বা থার্ড-পার্টি সার্ভারে অনাকাঙ্ক্ষিত রিকোয়েস্ট পাঠাতে ।
* **ক্ষতি:** অভ্যন্তরীণ নেটওয়ার্কের গোপন সার্ভিস ও মেটাডাটা ফাঁস হওয়া।
* **প্রতিরোধ:**
  * সার্ভার সাইডে ইউআরএল (URL) ভালোভাবে ভ্যালিডেট ও সেনিটাইজ করা।
  * সার্ভারের জন্য ইন্টারনাল লুপব্যাক (`127.0.0.1`) অ্যাক্সেস সীমাবদ্ধ করা।

---

### ৫. OS Command Injection
* **কী এবং কেন হয়?** অ্যাপ্লিকেশন ইনপুটের মাধ্যমে অপারেটিং সিস্টেমের কমান্ড রান করিয়ে নেওয়া ।
* **ক্ষতি:** সম্পূর্ণ অপারেটিং সিস্টেম বা সার্ভারের নিয়ন্ত্রণ চলে যাওয়া (Remote Code Execution)।
* **প্রতিরোধ:**
  * সরাসরি শেলের মাধ্যমে কমান্ড চালানোর ফাংশন (যেমন: `exec()`, `eval()`) পরিহার করা।
  * প্রয়োজন হলে কমান্ড আর্গুমেন্ট আলাদা অ্যারে হিসেবে পাঠানো এবং কড়া ইনপুট ভ্যালিডেশন রাখা।

---

### ৬. Broken Access Control (BOLA / IDOR)
* **কী এবং কেন হয়?** ইউআরএল বা API পাথের আইডি পরিবর্তন করে অন্য ব্যবহারকারীর ডাটা দেখা বা পরিবর্তন করা ।
* **ক্ষতি:** অননুমোদিতভাবে অন্যের ডাটা পরিবর্তন বা দেখা।
* **প্রতিরোধ:**
  * প্রতিটি ডাটাবেজ রিকোয়েস্টে বা সার্ভিস লেয়ারে ইউজার অথরাইজেশন চেক নিশ্চিত করা (`req.user.id === resource.owner_id`) ।

##  ৩. সেশন ও অথেনটিকেশনের বেস্ট প্র্যাকটিস

* **পাসওয়ার্ড (Password):** কখনো প্লেন টেক্সট পাসওয়ার্ড সেভ করা যাবে না। সবসময় **Argon2** বা **Bcrypt** ব্যবহার করে সল্টসহ হ্যাশ (Hash) করে সেভ করতে হবে।
* **JWT Tokens:** ছোট মেয়াদের Access Token এবং নিরাপদ Refresh Token প্যাটার্ন ব্যবহার করা। Token-এর Expire Date (`exp`) ও Signature যাচাই করা।
* **Session Cookies:** কুকিতে অবশ্যই `Secure`, `HttpOnly`, এবং `SameSite` ফ্ল্যাগ ব্যবহার করা ।
* **Rate Limiting:** ব্রুট-ফোর্স অ্যাটাক ঠেকানোর জন্য সংবেদনশীল এন্ডপয়েন্টে (যেমন: Login, Signup) Redis ভিত্তিক Rate Limiter বসানো।
