#  Understanding Routing in Backend Development

এই নোটে ব্যাকএন্ড ডেভেলপমেন্টের একটি অন্যতম মূল ধারণা **Routing (রাউটিং)** এবং এর বিভিন্ন ধরন সম্পর্কে বিস্তারিত আলোচনা করা হলো।

---

##  ১. Routing কি? (What is Routing?)

* **Intent vs Location:** 
  * **HTTP Method:** রিকোয়েস্টের **"What"** বা উদ্দেশ্য প্রকাশ করে (যেমন: `GET` = ডেটা নেওয়া, `POST` = ডেটা তৈরি করা)।
  * **Route/URL Path:** রিকোয়েস্টের **"Where"** বা ঠিকানা প্রকাশ করে (কোন রিসোর্সে কাজটি সম্পাদন করতে হবে)।
* **মূল সংজ্ঞা:** ব্যাকএন্ডে **Routing** হলো ক্লায়েন্ট থেকে আসা URL Parameter/Path এবং HTTP Method-কে নির্দিষ্ট একটি **Server-side Handler** বা বিজনেস লজিকের সাথে ম্যাপিং (Mapping) করা।
* **কীভাবে কাজ করে:** সার্ভার মূলত `[HTTP Method + Route Path]`-কে একটি ইউনিক Key হিসেবে বিবেচনা করে রিকোয়েস্টটিকে সঠিক হ্যান্ডলারে পাঠায়।

---

## ২. Static vs Dynamic Routes

### ১. Static Routes (স্ট্যাটিক রাউট)
* **সংজ্ঞা:** যে রাউটগুলোর পাথ সবসময় ফিক্সড বা ধ্রুবক (Constant) থাকে এবং এতে কোনো পরিবর্তনশীল প্যারামিটার থাকে না।
* **উদাহরণ:** 
  * `GET /api/books`
  * `POST /api/books`

### ২. Dynamic Routes (ডাইনামিক রাউট)
* **সংজ্ঞা:** যে রাউটগুলোতে পরিবর্তনশীল ভ্যালু বা প্যারামিটার গ্রহণ করা যায়।
* **Path / Route Parameter:** রাউট পাথের ভেতরের পরিবর্তনশীল অংশকে Path Parameter বলা হয়। সার্ভার ফ্রেমওয়ার্কগুলোতে সাধারণত `:` (Colon) দিয়ে এটি প্রকাশ করা হয়।
* **উদাহরণ:** `GET /api/users/:id`
  * বাস্তব রিকোয়েস্ট: `GET /api/users/123`
  * এখানে `123` অংশটি `id` প্যারামিটারে অ্যাসাইন হয় এবং সার্ভার নির্দিষ্ট ওই আইডি-র ইউজারের ডেটা প্রসেস করে।

---

##  ৩. Query Parameters (কোয়েরি প্যারামিটার)

* **সংজ্ঞা:** URL-এর শেষে `?` চিহ্নের পর Key-Value আকারে তথ্য পাঠানোর মেকানিজমকে Query Parameter বলে।
* **কেন ব্যবহার করা হয়:** 
  * `GET` রিকোয়েস্টে কোনো Request Body থাকে না। তাই অতিরিক্ত তথ্য বা ফিল্টারিং মেটাডেটা পাঠানোর জন্য কোয়েরি প্যারামিটার ব্যবহার করা হয়।
* **ব্যবহারের ক্ষেত্র:**
  * **Search Filtering:** `/api/search?query=javascript`
  * **Pagination:** `/api/books?page=2&limit=20`
  * **Sorting:** `/api/products?sort=asc`

---

##  ৪. Nested Routes (নেস্টেড রাউট)

* **সংজ্ঞা:** একের অধিক রিসোর্সের মধ্যে সম্পর্ক (Hierarchy/Relationship) প্রকাশ করার জন্য রাউটগুলোকে একটার ভেতর আরেকটা চেইন বা নেস্ট করা হয়।
* **সুবিধা:** REST API-এর লজিক্যাল এবং রিডেবল স্ট্রাকচার তৈরি করতে সাহায্য করে।
* **উদাহরণ:** 
  * `GET /api/users/123/posts/456`
  * **অর্থ:** ইউজার আইডি `123`-এর নির্দিষ্ট পোস্ট আইডি `456`-এর বিস্তারিত তথ্য ফেচ করা।

---

##  ৫. Route Versioning & Deprecation

* **কেন প্রয়োজন:** API-এর স্ট্রাকচার পরিবর্তন হলে বা Breaking Changes আনলে যেন পুরনো ক্লায়েন্ট অ্যাপ (যেমন: মোবাইল অ্যাপের পুরনো ভার্সন) ভেঙে না যায়।
* **কাজ করার পদ্ধতি:**
  * **Version 1:** `GET /api/v1/products` (পুরনো রেসপন্স স্ট্রাকচার)
  * **Version 2:** `GET /api/v2/products` (নতুন রেসপন্স স্ট্রাকচার)
* **Deprecation Workflow:** ডেভেলপারেরা প্রথমে নতুন ভার্সন (`v2`) রিলিজ করেন এবং ক্লায়েন্ট টিমকে সময় দেন ট্রান্সফার হওয়ার জন্য। নির্দিষ্ট সময় পর পুরনো ভার্সনটি (`v1`) বন্ধ/অকার্যকর (Deprecate) করে দেওয়া হয়।

---

##  ৬. Catch-All Route (Fallback Routing)

* **সংজ্ঞা:** সার্ভারে সংজ্ঞায়িত করা নেই—এমন কোনো অনাকাঙ্ক্ষিত বা ভুল রাউটে রিকোয়েস্ট আসলে সেটি হ্যান্ডেল করার মেকানিজম।
* **কাজ করার পদ্ধতি:** রাউট তালিকার একদম শেষে Wildcard (`*`) দিয়ে এটি ডিফাইন করা হয়।
* **উদাহরণ:** `GET /api/v3/invalid-path`
  * সার্ভার একটি ইউজার-ফ্রেন্ডলি রেসপন্স ও স্ট্যাটাস কোড প্রদান করে: `404 Not Found` - "Route does not exist."
